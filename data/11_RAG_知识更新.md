# 🔄 RAG 知识更新

> 路径：AI Agent / 📚 RAG
>
> https://app.notion.com/p/3d1776baec49814a83dbeacc5ddded7d?pvs=204

RAG 的一个重要优势，就是把“知识”从 LLM 参数中拆出来。于是知识库内容变化时，通常不需要重新训练 LLM。
## 1. 文档发生变化时，更新哪一层？
典型链路是：
**Document 变化 → 找到受影响的 Chunk → 重新 Embedding → 更新 Vector DB / Index**
如果文档新增内容，就增加对应 Chunk；如果内容被修改，就重新生成受影响 Chunk 的向量；如果文档被删除，就删除对应记录。
因此一个可用的 RAG 系统必须把 **Document、Chunk、Vector、Metadata** 的关系管理好，而不是只会“第一次建库”。
## 2. 为什么不用重新训练 LLM？
因为 LLM 和外部知识库承担的是不同职责：
- LLM：负责语言理解、推理和生成
- RAG：负责在外部知识中寻找当前需要的信息
知识库里的政策、产品说明、内部文档每天变化，并不意味着模型的语言能力发生变化。
## 3. 增量更新为什么重要？
如果一本知识库只有一个文件发生修改，没有必要把所有文件重新 Embedding。系统可以定位受影响的 Chunk，只更新这一部分。
这就是增量更新的基本思想：**变化发生在哪里，就尽量只重建哪里。**
## 4. 一个特别容易混淆的情况：Embedding Model 变了
“文档变了”和“Embedding Model 变了”不是同一种更新。
如果只是 Document 变化，通常只需重新处理受影响 Chunk。
如果 Embedding Model 更换，旧 Vector 和新 Vector 往往属于不同的向量空间，不能直接混用。此时通常需要对整个知识库重新 Embedding，或者在迁移期间维护新旧索引。
## 5. Metadata 也会影响更新
即使 Chunk 文本没有变化，权限、版本、来源、时间等 Metadata 变化，也可能改变检索结果。因此知识更新不只是“重新算向量”，还包括结构化信息的同步。
最终可以把 RAG 知识维护理解成：
> **内容变化 → 找到影响范围 → 更新表示 → 同步存储与索引 → 保证旧知识不会继续被错误召回。**
