## 2. Agent 与对话历史

### P01：保留“调用请求”和“执行结果”这一对消息

**位置**：[ReAct_agent.py](D:/code/my-agent/ReAct_agent.py:122)，`run()` 中保存 assistant 工具调用消息，以及随后保存 tool 消息的部分。

**当时的问题**：为什么执行完工具后，还要把模型发出的 `assistant(tool_calls)` 放进历史？

请求和结果靠同一个编号连接：

```text
assistant：调用 retrieval，这次调用编号为 call_001
tool：这是 call_001 的检索结果
```

模型下一次调用所能看到的记录，来自代码传入的 `messages`。Python 曾经执行过工具，不等于请求和结果已经完整出现在这份记录中。

**证据**：用户说：“我试过删掉，模型会调两次工具，它记不得自己调过了。”这是用户观察到的一次行为。不能扩大成“删掉就必然重复调用”，也不能把所有重复调用都归因于这个问题。

**当前状态**：代码保留了调用请求，也为每个调用返回对应 `tool_call_id` 的结果。工具循环离线测试通过。

**回查对话关键词**：`tool_call_id`、`我试过删掉`。

### P02：提示词写了次数限制，程序也需要明确执行限制

**位置**：[ReAct_agent.py](D:/code/my-agent/ReAct_agent.py:100)，`run()` 中的 `retrieval_count` 和限制分支。

原来提示词说“同一个问题最多检索两次”，代码只有 `max_steps=5`。`max_steps` 限制的是模型调用轮数；一次模型回复还可能提出多个工具调用，所以它不等于检索次数限制。

用户随后补了计数：每次 `run()` 从零开始，参数校验通过后，最多执行两次 retrieval。

**中间出现过的问题**：第三次被拒绝后用了 `return`，直接结束整个 `run()`。模型读不到拒绝说明，同批后续工具也可能没有对应结果。

**修正**：追加带原调用编号的 tool 消息后使用 `continue`，继续处理同批其他工具，随后让外层循环再次调用模型。

**Codex 离线验证**：一次请求“三次 retrieval ＋ 一次时间工具”时，只执行两次检索，第三次有拒绝结果，时间工具仍执行；下一轮计数重新开始。参数解析或校验失败也有对应结果。

**边界**：两次限制数的是工具执行机会，不是 HTTP 请求数。单次工具执行内部仍可能重试，见 P08。

**回查对话关键词**：`return 换成 continue`、`最多检索两次`。

### P03：同一份对话状态应由添加、读取、清空和模型调用共同使用

**位置**：[agent.py](D:/code/my-agent/agent.py:17)，初始化、`add_message()`、`clear_history()`、`get_history()`；以及 ReAct 的 `run()`。

原来基类写 `_history`，子类实际使用 `messages`。因此，继承来的读取和清空方法操作不到实际对话。

用户先在子类重写读取、清空方法，随后把历史统一放到基类的 `messages`，删除或注释子类的重复实现。

**当前状态**：有效代码中的添加、读取、清空和模型调用都使用 `messages`。旧 `_history` 裁剪代码只留在注释中。

**Codex 离线验证**：

```text
添加测试消息后：['system', 'user']
清空后：        ['system']
```

清空 `get_history()` 返回的列表，不会清掉内部列表。

**边界**：`list.copy()` 是浅拷贝。返回列表中的消息字典仍与内部共享；修改其中字典的内容，仍可能影响内部状态。目前只说明这个行为，没有认定它必须立即改成深拷贝。

**回查对话关键词**：`实际对话`、`获取历史`、`同一个 messages`。

### P04：清空历史时，保持与初始化相同的 system prompt 规则

**位置**：[agent.py](D:/code/my-agent/agent.py:31)，`clear_history()`。

中间版本无条件重建 system 消息。但基类允许 `system_prompt=None`，这样会生成 `{'role': 'system', 'content': None}`。

**当前修正**：先建立空列表，有 system prompt 时才添加 system 消息。这与初始化行为一致。

**证据**：旧行为经过 Codex 离线复现，当前实现已经按建议修改；有 system prompt 的清空测试通过。

### P05：裁到 user 边界能保留配对，但可能把最新完整轮也丢掉

**位置**：[ReAct_agent.py](D:/code/my-agent/ReAct_agent.py:40)，`_trim_history()`。

当前策略先按条数取末尾窗口，再丢弃开头不是 user 的消息。如果最新一轮本身超过窗口，它的 user 消息就不在窗口中；后面的 assistant/tool 会全部被丢掉，只剩 system。

**Codex 离线复现**：设置 `max_history_length=5`，输入一轮含两次工具调用的历史：

```text
裁剪前：system, user, assistant, tool, assistant, tool, assistant
裁剪后：system
```

这不是“工具结果悬空”的复现，配对没有被留下一半；实际问题是整轮上下文丢失。

**建议待讨论**：按完整轮选择保留内容，并明确“最新一轮超过预算”怎么办。例如保留最新完整轮、接受软上限，或者做摘要与内容预算。不同选择有不同取舍，尚未实现和对照验证。

**当前状态**：旧问题仍在，不应写成 DeepSeek 本次修改引入的新错误。

## 3. 重试与 embedding 对齐

### P06：rerank 的 requests 异常原来不在重试清单中

**位置**：[retry.py](D:/code/my-agent/retry.py:44) 的 `with_retry()`，以及 [llm.py](D:/code/my-agent/llm.py:68) 的 `rerank()`。

原重试函数只处理 OpenAI SDK 异常；rerank 用 requests，超时、连接失败、HTTPError 属于另一组异常。外面写了 `with_retry`，并不意味着能捕获这些异常。

**DeepSeek 的改动**：允许调用方提供异常清单；rerank 显式使用 requests 清单，5xx 通过 `raise_for_status()` 抛出可重试错误。

**Codex 离线验证**：把 `requests.post` 替换成模拟响应，结果为：

| 响应序列 | 实际调用次数 | 结果 |
|---|---:|---|
| 500，然后 200 | 2 | 成功恢复 |
| 401，然后 200 | 1 | 立即失败，不重试；符合该认证失败场景 |
| 429，然后 200 | 1 | 立即失败；这是 P07 |

**结论**：requests 重试链路已经接通，但不能把“所有 4xx 都无需重试”当作通用规则。

### P07：rerank 把 429 限流归进了永久错误分支

**位置**：[llm.py](D:/code/my-agent/llm.py:90)，`rerank()` 的 `status_code >= 400` 分支。

**通俗解释**：服务端说“你请求得太频繁了，等一下”，程序却按“这次请求永远无法成功”退出了。

当前代码把 429 转为 `ValueError`，而这个异常不在 rerank 重试清单中。

**Codex 离线复现**：预设第一次 429、第二次 200。实际只调用一次，抛出 `ValueError`，第二个成功响应没有被使用。这里指的是走 requests 的 rerank，不能扩大成“整个项目里的 429 都不重试”。

**建议待实施**：把限流状态单独分类，在有预算的情况下等待后重试；若服务端提供 `Retry-After`，考虑它所要求的等待时间。401、参数错误等情形仍分别处理。

**外部依据**：[RFC 6585 的 429 定义](https://www.rfc-editor.org/rfc/rfc6585#section-4) 说明了限流及可选的 `Retry-After`。

**当前状态**：待处理，未改代码。

### P08：三层各自重试，会把总请求数放大

**位置**：[tool_executor.py](D:/code/my-agent/tool_executor.py:98) 的工具层重试、[llm.py](D:/code/my-agent/llm.py:57) 的 `embed()` 重试，以及 [llm.py](D:/code/my-agent/llm.py:26) 创建的 SDK 客户端。

**通俗解释**：里面一层已经试了多次，仍然失败。外面一层收到失败后，又让它整套重新来过。

本地验证使用的 OpenAI SDK 版本是 **3.16.2**，该客户端的 `max_retries` 为 **2**，即初始请求加两次重试。项目自己的两层预算各为初始尝试加三次重试。

```text
工具层：4 次尝试
LLM 包装层：每次工具尝试最多再试 4 次
SDK：每次包装层尝试最多再发 3 次 HTTP 请求

总数：4 × 4 × 3 = 48
```

**Codex 离线验证**：使用当前真实 `ToolExecutor`、`LLM.embed()` 和已安装 SDK；HTTPX `MockTransport` 对每次 embedding 请求都返回 500，关闭等待但保留重试控制流程。计数器得到 **48 次模拟 HTTP 请求**，最后错误被转换为工具结果。没有发送真实网络请求。

**成立条件**：这是该版本和预算下，持续可重试失败的路径。正常成功、永久错误或中途恢复会提前停止，不是每次运行都会请求 48 次。

**与 DeepSeek 笔记的关系**：其 P12 的两层 `4 × 4 = 16` 能说明外层与内层相乘；本次验证再把 SDK 自身的重试算进去，得到 48。两者的计数范围不同。

**建议待实施**：先确定谁拥有网络请求的重试预算。移除工具层重跑整个工具的重复保护后，还要处理 LLM 包装层与 SDK 的重复保护；仅移除工具层，在这个持续 500 的例子中仍可能是 `4 × 3 = 12` 次。保留自定义重试或保留 SDK 重试，都需要明确选择。

**当前状态**：待处理，未改代码。这个叠加问题原来已有，不应把它全算作 DeepSeek 新引入。

**回查对话关键词**：`48 次`、`三层代码都在帮它重试`。

### P09：embedding 使用返回 index 与原文配对

**位置**：[RAG_tool.py](D:/code/my-agent/RAG_tool.py:51)，`build_store()`。

原来 `zip(batch, resp.data)` 按列表位置把文档和向量配对。响应数量不足时会静默截断；若响应顺序与请求不一致，可能配错。

“服务端实际会乱序”没有在本对话中通过真实接口证明。风险与已经发生的故障要分开写。

**DeepSeek 的改动**：按 `item.index` 建映射，检查唯一索引数量，再按原请求编号取向量。

**Codex 离线对照**：

| 模拟响应 | 当前实现结果 |
|---|---|
| 正常顺序 | 正确配对，与旧行为一致 |
| 乱序 `[1, 0]` | 仍按请求编号正确配对 |
| 少返回一条 | 明确抛 `RuntimeError` |
| 两条响应重复使用同一索引 | 明确抛 `RuntimeError` |
| 两条响应使用越界索引 `[1, 2]` | 抛 `KeyError`，没有继续保存错误结果 |
| 多个批次，各自从 0 编号 | 正确处理 |

这说明改动对这些用例有效，不能扩大成“所有异常响应都已验证”。

**缓存边界**：修改 `build_store()` 没有改变缓存指纹。若旧版曾写入错配数据，新版可能继续读它；但我们没有证明当前缓存有错，不能据此要求立即清缓存、重新花费接口调用。

**当前状态**：对齐改动合理；旧缓存只记录为条件风险。

### P10：实验接入正式 retrieval 时，要同步变量与数据形状

**时间与授权**：2026-10-11，用户说：“我已经改了 `retrieval()` 了，你帮我看看，不对的话帮我改了。”这次授权只涉及混合检索接入，不顺带处理 P07、P08 等已记录事项。

**位置**：[RAG_tool.py](D:/code/my-agent/RAG_tool.py:173)，`retrieval()`。

发现并修正了四处问题：

1. **旧变量名残留。** 已计算 `vector_scores`，排序仍用 `np.argsort(-scores)`。导入模块调用时可能出现 `NameError`；改为使用当前问题的 `vector_scores`。
2. **融合结果的形状变了。** `fused_results` 每项是 `(chunk_id, rrf_score)`，原代码把整项当作 `store` 下标。改为先解包，再按 `chunk_id` 取正文和来源，融合分数明确存为 `rrf_score`。
3. **融合后仍用余弦阈值。** 旧候选构建代码再次按余弦 `0.4` 过滤，可能把 BM25 单独找回的片段排除。余弦阈值留在向量路；两路融合后使用并集，最终按已有 rerank 阈值筛选。
4. **候选预算会压掉关键词路独有结果。** 每路取 20 条，融合后原来又截成 20 条。向量权重 2、BM25 权重 1、RRF 常数 60 时：

   ```text
   向量第 20 名的独有贡献 = 2/80 = 0.025
   BM25 第 1 名的独有贡献 = 1/61 ≈ 0.016393
   ```

   因此向量路满 20 条时，每个向量候选都高于任何 BM25 独有候选；后者进不了融合前 20。修正为保留两路完整去重并集，最多 40 条送 rerank。权重仍为 `2:1`，代价是单次重排可能处理更多文本。

**验证**：对最新真实函数注入固定分数及假 rerank，7 个场景通过：BM25-only、向量-only、两路都空、候选去重、rerank 局部编号映射、rerank 低分拒答，以及“20 个向量候选＋1 个 BM25 独有候选”全部送入重排。

随后使用用户配置的真实 embedding、rerank 接口运行 `eval.py`：**9/9 通过，首选命中 7/7**，其中两个无关问题正确拒答。第一次在沙箱中连接被阻止；获准在沙箱外重跑后完成。语法解析和本次代码的差异空白检查也通过。

**结论边界**：这证明当前接入通过既有评测，没有在这组问题上退化；此前纯向量基线也是 9/9、首选 7/7，因此仍不能据此声称混合检索提升了质量。

## 5. RAG 学习建议与实际实验记录

### R01：混合检索从独立实验接入正式工具

**实验文件**：[bm25_test.py](D:/code/my-agent/bm25_test.py)、[rrf_test.py](D:/code/my-agent/rrf_test.py)。

**初次记录时**：`retrieval()` 仍是纯向量召回后 rerank，`get_index()` 尚未增加 BM25。

**随后更新**：用户为 `get_index()` 增加共享的 BM25 内存索引，再接入混合召回；Codex 修正 P10 所列问题。当前正式流程为向量与 BM25 两路召回、加权 RRF、rerank 和返回来源。

本对话的建议是在已有向量召回旁增加 BM25，再融合候选。它的价值需要用对照实验验证，不能因为多了一种算法就认定效果更好。

用户的三个文档实验说明了词项匹配的特点：查询 `HNSW为什么快` 时，含 HNSW 的文档约为 `0.498`，其他两条为 0；改成 `怎样提高查找速度` 后，三条都为 0。语义接近的说法，未必产生共同词项。

分词和打分时需要记住：文档与查询使用一致的处理规则；重复词要保留以统计词频；词项正分不等于已经证明语义相关；BM25 分数不是概率。

### R02：加权 RRF 的实际计算

用户提出“向量检索更重要”，实验采用向量权重 **2**、BM25 权重 **1**。这是设计假设，尚未证明是这个知识库的最优比例。

```text
一路贡献 = 该路权重 / (60 + 该片段在这一路的名次)
总分 = 两路贡献相加
```

名次从 1 开始。`60` 是实验选用的融合参数，不是从文档计算得到的值，也不是返回数量。某一路没有该片段，该路贡献为 0。

用户提供的问题是 **“HNSW为什么能加速检索”**，两份排名为：

```text
向量：[31, 32, 11, 7, 61]
BM25：[32, 7, 61, 60, 127]
```

| chunk 编号 | 计算过程 | RRF 总分，近似值 |
|---|---|---:|
| 32 | `2/62 + 1/61` | 0.048652 |
| 7 | `2/64 + 1/62` | 0.047379 |
| 61 | `2/65 + 1/63` | 0.046642 |
| 31 | `2/61 + 0` | 0.032787 |
| 11 | `2/63 + 0` | 0.031746 |
| 60 | `0 + 1/64` | 0.015625 |
| 127 | `0 + 1/65` | 0.015385 |

**证据**：Codex 计算过这些数值；用户运行 RRF 脚本确认相同。

两路各五条，其中三个编号重复，因此合并得到七个不同片段。编号是当前共享切块列表的下标，不是永久 ID。切块或语料变化后编号可能改变；两路必须使用相同版本、相同顺序的列表。

**回查对话关键词**：`为什么不加权重`、`结果怎么来的`。

### R03：rerank 返回候选列表的位置，需要映射回 chunk 编号

送入 rerank 的候选编号顺序是：

```text
候选位置： 0   1   2   3   4   5    6
chunk ID：32   7  61  31  11  60  127
```

所以返回 `index=3` 对应 chunk 31，需要用 `candidate_ids[3]` 映射；不能直接取 `chunks[3]`。

**用户实测结果**：

| rerank 顺序 | chunk 编号 | 分数 | 来源 |
|---:|---:|---:|---|
| 1 | 31 | 0.934 | `02_HNSW__ANN.md` |
| 2 | 61 | 0.790 | `08_Vector_DB.md` |
| 3 | 7 | 0.746 | `00_RAG.md` |
| 4 | 32 | 0.740 | `02_HNSW__ANN.md` |

31 的正文直接解释多层图如何加速搜索；在这次结果中，它从 RRF 第四变成 rerank 第一。这个顺序与用户给出的正文内容相符，不等于我们知道模型内部的全部打分理由。

**当时实验的验证边界**：最终四条都已经出现在原向量前五中，BM25 新增的 60、127 没有进入最终四条。因此本题证明组合流程可以运行，不能证明混合检索比纯向量更好。当时没有重跑完整 `eval.py`，历史 `9/9` 不能充当新流程的验收。随后实际完成的回归另见 P10。

### R04：接入建议与后续验证方向

1. **已接入**：BM25 放进共享的内存索引，按同一个 `store` 顺序建立；复用本地统计并对齐编号。
2. **已接入**：融合后再送 rerank；RRF、余弦和 rerank 分数分别使用，余弦阈值只用于向量路。
3. 用同一组有期望来源的问题，对比纯向量和混合检索，再讨论候选数量、权重和阈值。关键词无匹配时，不为凑数量把零分结果加入该路排名。
4. 标题目前主要在 chunk 的 `metadata` 中。未来可实验正文索引与“标题＋正文”索引的差异，目前没有证明哪种更好。

### 6.3 公式示例与所用库存在实现差异，之前没有说明

早期 BM25 手算例子使用了 Lucene 式的非负 IDF：

```text
ln(1 + (N - df + 0.5) / (df + 0.5))
```

后续代码使用 `rank_bm25.BM25Okapi`。整理时读取本地 **rank-bm25 0.2.2** 源码，确认它先计算：

```text
ln((N - df + 0.5) / (df + 0.5))
```

再处理负 IDF。两者的数字不能要求完全一致。这个差异是整理时补充确认的，应补讲，不能把前面的手算冒称为该库输出的逐位复现。
