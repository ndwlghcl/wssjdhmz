# 设计演进与踩坑笔记（my-agent）

> 配套阅读：`LangChain_RAG_学习笔记.md`（偏 API / 知识参考）。
> 本篇偏"**为什么这么做**"——记录框架从零到 RAG Agent 的设计演进、踩过的坑、调试方法。

## 一、全貌：到底在造什么

**Agent 的三要素**：

```
模型（LLM）  +  循环（run）  +  工具（Tool）
  会说话         会行动          有手脚
```

**分层与一句话职责**：

| 文件 | 封装了什么麻烦 |
|------|----------------|
| `config.py` | 参数从哪来（环境变量只在这里读一次，其他模块只认 Config）|
| `llm.py` | 怎么跟模型说话（`chat`/`think`/`stream`/`embed`/`rerank`，全部接入 `with_retry`；前三者走 OpenAI 协议用 `client`，`rerank` 是厂商私有协议用 `requests`）|
| `retry.py` | 公共重试引擎（OpenAI 临时错误分类 + 指数退避；重试用尽向上抛，善后归各层）|
| `agent.py` | 基类：name / llm / config / system_prompt + 抽象 `run()` |
| `tool.py` | 工具契约（`Tool` 基类 + `FunctionTool` + `@tool` 装饰器，签名自动推导 schema）|
| `tool_executor.py` | 注册/校验/执行（按名字查、`validate_args` 对照 schema 拦参数错、永不抛异常）|
| `chunking_test.py` | 真实文件 → 切块（按标题切 + 递归切 + 过滤垃圾块）|
| `RAG_tool.py` | 检索工具：两阶段（numpy 矩阵粗筛 → rerank 精排）+ 磁盘缓存 + 来源标注 |
| `ReAct_agent.py` | 主力 Agent：function calling 循环 + 多轮记忆 + 记忆裁剪 |
| `eval.py` | 检索回归测试（固定用例 → 命中率 / 首选率基线）|
| `test/inspect_query.py` | 检索诊断（打印某问题在两阶段的逐条排名）|
| `test/bench_cosine.py` | 打分性能基准（矩阵版 vs 纯 Python 版）|

> 已退役：`message.py`（见 2.2）、文本协议版循环（见 2.3）。

## 二、设计演进（按时间）

### 2.1 硬编码 → Config（单一事实来源）

最初 `LLM` 自己 `getenv`，`Config` 也 `getenv`，两边各读各的。
后来收口成：**只有 `Config` 认识环境变量名**，其他模块一律从 `Config` 取。

```python
@classmethod
def from_env(cls) -> "Config":
    return cls(default_model=os.getenv("LLM_MODEL_ID", ...), ...)
```

好处：加配置、改变量名、做校验，都只改一处。
细节：`api_key` 用 `Field(repr=False)` + `to_dict(exclude={"api_key"})`，**密钥不能出现在日志里**。

### 2.2 Message 的诞生与退役 ⭐

- **诞生**：只有聊天时，它是合理的——Pydantic 校验 role、带 timestamp/metadata、`to_dict()` 做协议转换。
- **失效**：function calling 来了，协议字段膨胀（`tool_calls`、`tool_call_id`…），手写类追不上；而且 `timestamp/metadata` **从头到尾没人用过**。
- **退役**：全框架改用**协议原生的字典**，`message.py` 归档到 `test/废弃/`。

**教训**：抽象不是一次成型、也不是永久的。判断它是否该留：**看它现在还在不在创造价值**。
被否掉的另一方案："信封模式"（用类包一个 payload 字典）——设计正确但当前用不上，属于为想象需求造抽象（YAGNI）。

### 2.3 文本协议 → function calling ⭐

| | 文本协议（旧） | function calling（现） |
|---|---|---|
| 工具怎么给模型 | 拼进提示词的工具清单文字 | `tools=` 参数，JSON Schema |
| 模型怎么表达调用 | 输出 `Action: 工具名[参数]` | 返回 `message.tool_calls` 结构体 |
| 结果怎么回传 | 拼进提示词历史文字 | `{"role":"tool","tool_call_id":...,"content":...}` |
| 何时结束 | 提示词约定 `Finish[...]` | 不返回 tool_calls 就是答案 |

**被删掉的整套防线**（都不再需要）：正则解析 `_parse_action`、防自造 Observation 检测、格式纠错提示。

两条必须记住的协议铁律：
1. **带 `tool_calls` 的助手消息必须原样存回历史**（`tool` 消息要靠 `tool_call_id` 引用它）
2. **`arguments` 是 JSON 字符串**，要 `json.loads` 成字典

> 实测教训：缺了第 1 条，**严格服务端会 400；宽容的第三方服务端不报错，但模型会重复调用同一个工具**（看不到自己调用过）。
> **不报错 ≠ 没问题**——静默失败比报错更贵。

### 2.4 记忆：从 history 到 messages

- ReActAgent 自己维护 `self.messages: list[dict]`（不依赖基类的 `_history`）。
- 裁剪策略（`_trim_history`）：
  1. **system 永远保留**
  2. **裁剪后第一条业务消息必须是 `user`**——一轮对话总以 user 开始，切在 user 处就绝不会切断"assistant(tool_calls) + tool"的配对
- 存入历史前对超长工具结果**截断**（`max_obs_tokens`），防 token 膨胀。

### 2.5 工具：类 → 装饰器 → 自动 schema

- 一开始每种工具写一个类，太重 → 改 `@tool` 装饰器（内部生成 `FunctionTool`）。
- **装饰器机制**：`@tool(...)` 只是两次调用的语法糖——`tool(...)` 先吃配置参数并返回 `decorator`；`@` 再把被装饰的函数作为**唯一位置参数**传给 `decorator`。参数名、类型标注都不参与匹配。
- `@tool` 的参数 schema 用 `inspect.signature()` **从函数签名自动推导**（Python 类型 → JSON 类型对照表；无默认值 = 必填），不用手写。

### 2.6 schema 生成器升级：泛型修复 + Annotated 参数描述 ⭐

初版 schema 推导的两个盲区（外部评审指出，实测确认）：

1. **泛型标注识别错**：`list[str]` 是 `GenericAlias` 对象，不等于对照表里的键 `list`，查表 miss 后**静默降级成 `"string"`**——模型拿到错误说明书，还不报错。修法不是往表里穷举（`list[int]`/`list[Note]`… 是无穷族），而是先 `get_origin()` 剥出骨架再查；`get_args()` 顺手把元素类型写进 `items`。**无穷族靠归约，不靠穷举。**
2. **参数没有描述**：模型只能靠参数名猜语义（`input` 这种名字近乎为零）。引入 `typing.Annotated[str, "要检索的问题…"]`，描述贴在参数旁、自动进 schema 的 `description`。注意 `get_type_hints` 必须传 `include_extras=True`，否则元数据被剥掉。工具描述质量直接影响模型填参准确率。

顺带踩坑：装饰后的 `FunctionTool` 对象不能直接喂 `inspect.signature`——schema 在装饰那一刻就生成好了，测试要走"装饰 → 注册 → `get_tools_schema()`"生产路径。

### 2.7 重试下沉：retry.py 公共引擎 ⭐

评审发现"重试保护了工具，却没保护 LLM 调用"：`TRANSIENT_EXCEPTIONS` 里全是 OpenAI API 层的错（工具里唯一会抛它的是 retrieval 内部的 embedding 调用），`llm.chat` 反而裸奔——一次 429 整个 run 崩掉，而工具的网络抖动能自愈，主次颠倒。

重构：抽 `retry.py`（`with_retry` + `TRANSIENT_EXCEPTIONS`），`chat / stream / embed` 与工具执行共用。关键设计点：

- **重试策略与"用尽后怎么办"分离**：`with_retry` 默认向上抛，善后由各层契约表达——工具层"永不抛异常，错误转观察结果喂回模型"；LLM 层"模型挂了没有喂回通道，抛给调用方兜底"。
- **stream 只包连接阶段**：生成器一旦开始吐字就不能整体重试，否则内容重复输出。
- 定位原则：**横切关注点（重试/超时）放在拥有外部依赖的那一层**（llm.py），谁调 API 谁自动继承；补丁位置应该反映病根，不是第一次疼的地方。
- 补充认知：openai SDK 自带 `max_retries=2` 的隐式重试，但薄（背靠背两次、无长退避）且不可见，替代不了显式策略。

### 2.8 检索升级：粗筛 + rerank 精排 ⭐

**为什么要 rerank**：向量检索是**双塔（bi-encoder）**——query 和文档各自独立编码，只比最后那两个向量；快（可预计算）但**两者从未"见面"**，只能判断"像不像"。rerank 是**交叉编码（cross-encoder）**——query 和文档拼在一起进模型做注意力交互，准得多，但**无法预计算**，只能对少量候选现算。

于是形成标准两阶段：

```
余弦粗筛 top 20（召回：宁多勿漏）→ rerank 精排 top 4（精排：宁准勿滥）→ 喂给大模型
```

**实测三大价值**（同一批数据、rerank 前后对比）：

1. **纠正排序**：俄耳甫斯问题，余弦首选"一个更喜欢的表达"(0.850)，rerank 判定"我们的观点"(0.992) 更切题
2. **压制噪声**：`33_我们的思考.md > 主题`（目录块）从余弦第 4 名落到阈值之外
3. **捞回跨文件内容**：Chunking 问题里 rerank 捞出余弦前 5 之外的 `13_Context_Assembly.md`(0.83)——**这条只有候选池够宽才可能发生**

**协议差异（为什么不走 client）**：OpenAI 协议里**没有 rerank 端点**。百炼的 rerank 是私有协议（`/api/v1/services/rerank/text-rerank/text-rerank`，请求体是嵌套的 `input`/`parameters`，结果在 `output.results`）→ 只能用 `requests` 直发。但**它仍然收口在 llm.py**：统一的是"模型调用都归一层"，不是"都用同一个客户端"。

**两阶段阈值必须分开定**（量纲不同，实测）：

| 阶段 | 相关问题 | 无关问题 | 阈值 |
|---|---|---|---|
| 余弦（粗筛） | ≥0.589 | ≤0.260 | `RECALL_THRESHOLD = 0.4` |
| rerank（精排） | ≥0.571 | ≤0.292 | `RERANK_THRESHOLD = 0.4` |

**教训**：引入新阶段，旧阈值全部作废。`SIM_THRESHOLD=0.5` 是余弦时代的数字——换成两阶段后它既不该管粗筛（太严会拦掉候选，rerank 没了素材），也不适用于精排（量纲不同）。

## 三、RAG 的关键决策

### 3.1 切块：结构化 > 固定长度

知识库是结构化 Markdown（39 篇笔记），所以：

```
MarkdownHeaderTextSplitter（按 # ## ### 切 → 标题进 metadata）
  ↓
RecursiveCharacterTextSplitter（chunk_size=500, overlap=50, separators 含中文句号"。"）
```

- `chunk_overlap` 保留的是**完整分隔单元**（一句话/一行），单元的 token 预算超了就不重叠。中文一句 20~40 字，所以 overlap 至少 50 才稳定。
- metadata 要在**切之前**打到 Document 上，子块才继承得到。

### 3.2 过滤垃圾块（实测有效）

**现象**：251 块时，问"Chunking 有哪些策略"，第 1 名居然是文件头的 `"> 路径：AI Agent / 📚 RAG > https://..."` 块（0.727），把真正的答案挤到第 3 名。

**原因**：垃圾块由高频词（RAG、AI Agent、路径、URL）组成，向量方向和很多问题都"靠得近"。

**解法**：切完过滤——

```python
def _is_noise(text: str) -> bool:
    t = text.strip()
    if len(t) < 30:              # 太短，无信息量
        return True
    if t.startswith("> 路径"):   # 文件头的路径/链接块
        return True
    return False
```

**效果**：251 → **198 块**（过滤 53 个），"Chunking 策略"的 top-1 从垃圾块变成真正的内容块。

### 3.3 嵌入：分批 + 上下文前缀 + 模型进指纹

- DashScope `text-embedding-v3` **单次最多 10 条**，必须分批（`batch_size=10`），`zip(batch, resp.data)` 保证顺序对齐。
- **模型名要纳入缓存指纹**：换了嵌入模型后旧向量不能复用，否则相似度全乱且不报错。
- （进阶、未做）`embed_text = "文件名 > 章节\n正文"` 给向量补上下文。

### 3.4 检索参数：全部用数据定，不靠猜

校准脚本同时打印**两段**分数分布（余弦 top5 + rerank top5），两套阈值一起定：

| 阶段 | 相关问题 | 无关问题 | 结论 |
|---|---|---|---|
| 余弦（粗筛） | 0.589 ~ 0.850 | ≤ 0.260 | `RECALL_THRESHOLD = 0.4` |
| rerank（精排） | 0.571 ~ 0.999 | ≤ 0.292 | `RERANK_THRESHOLD = 0.4` |

两条线都取"中间偏保守"。**实测分布要写进代码注释**——否则半年后看到 `0.4` 完全不知道它怎么来的。

**参数不是一次定终身**：本次就观察到分数整体位移（"草莓蛋糕"最高余弦从 0.418 掉到 0.260）——**语料或嵌入模型一变，所有阈值必须重新校准**。

**另一个坑**：早期 `top_k=3` 而知识库只有 3 篇文档 → 每次都返回全部内容，**排序彻底失效，检索退化成"全塞给模型"**。
→ `top_k` 必须小于候选总数，否则排序无意义。

### 3.5 缓存：缓存"昂贵"的，不缓存"便宜"的

- 嵌入 = 网络 + 钱 + 几十秒 → **值得缓存**；切块 = 本地 + 毫秒 → **不值得**。
- 实现：惰性初始化（`get_store()` 第一次调用才建；**import 阶段只准做便宜的事**——读文件/切块可以，调 API 不行）+ 磁盘缓存（`.embedding_cache.json`）。
- 失效判断：**指纹**（sha256：文档正文 + metadata + 嵌入模型名，逐块 `h.update`）——按内容失效，不受文件改动时间干扰。
- 缓存是"优化"不是"功能"：读/写失败都要 `try/except` 降级成"重新构建"，不能让主流程崩。

**缓存格式：pickle → JSON**（用 198 块 / 20 万个浮点的真实数据实测）：

| | pickle（旧） | JSON（现） |
|---|---|---|
| 往返精度 | ✓ | ✓（最短往返表示，逐位相等）|
| 体积 | 1.9 MB | 4.6 MB（文本浮点约 2.4 倍）|
| 加载耗时 | 5 ms | 82 ms（启动仅一次，无感）|
| 可读性 | 二进制 | 明文，可 grep、可手工排查 |
| 安全 | **load 即执行字节码** | 纯解析，不可能执行代码 |

- pickle 的本质：**不是数据格式，是"重建对象的程序"**——.pkl 是栈式虚拟机的操作码，`__reduce__` 声明"重建我 = 调用某函数"，恶意文件可借此执行任意代码。教训：**判断格式安全与否，问"load 过程会不会 import、会不会调用函数"**。
- pickle 存自定义类 = 存"类名 + 模块名"，加载端类必须原样存在，重构改名后旧缓存变死文件且**加载时才崩**；JSON 的限制（set/datetime 写不进）反而把约束暴露在写入时。显式限制 > 隐式宽容。
- JSON 的类型变形要记住：tuple 读回变 list、数字键变字符串键。
- 选型判断式：**数据形状 × 信任边界 × 体量**。store 是纯数据 + 内部缓存 + 小体量 → JSON 全赢；将来塞大数组再考虑专业二进制（.npy/parquet）。
- 两个 Windows 坑：`encoding="utf-8"` 必须显式写（文本模式默认 GBK）；`ensure_ascii=False` 否则中文全转 `\uXXXX`。

### 3.6 返回格式：带上"来源 + 相关度"

```python
f"[来源 {source} | 章节 {h1} > {h2}] [相关度 {score:.2f}]\n{text}"
```

模型才能引用来源（实测回答末尾会出现"（来源：01_Chunking.md > 4. Chunking 的常见策略）"），也便于人排查。

补充：有些块直接在 h1 之下（Notion 导出的文件有两个 h1，引言段不在任何 `##` 下），章节字段会空白 → 输出时回退 `h2 or h3 or "引言"`。

### 3.7 打分提速：numpy 矩阵视图（实测 620x）⭐

- **思维转变**：不是"把函数换成 numpy"，而是**去掉循环**——198 次点积合并成一次矩阵运算 `matrix @ q`。
- **视图 ≠ 另一份存储**：`store` 仍是唯一数据源；`matrix` / `norms` 只是同一份数据换种摆放方式，靠索引对齐（矩阵第 i 行 == store 第 i 项）。`argsort` 返回的就是索引，用它回 store 取 text/metadata。
- **"顺序稳定"是前提**：建索引时用 `sorted(glob)`，重建后顺序不变，视图永远对得上。
- 踩坑：若每次调用才 `np.array(list)` 转换，**转换开销会吃掉收益**（每查询 198×2 次转换）→ 视图要在拿索引时一次性建好。
- numpy 类型"出门要转"：`float(...)` 转回 Python float；存盘要 `.tolist()`（ndarray 不能直接 `json.dump`）。
- 实测（`test/bench_cosine.py`）：**37 ms → 0.06 ms/次，620x**（纯 Python 每维运算都走解释器，numpy 下沉到 C 层并利用 SIMD）。

### 3.8 检索评估：把一次验收变成可重复的回归测试 ⭐

- **只测检索，不测回答**：回答是模型生成的、措辞有随机性；检索命中哪个文件是确定性的 → 才适合做"通过/失败"判定。
- 两个指标：**命中率**（期望文件出现在结果里）+ **首选率**（排在第一位）。当前基线：`9/9`、`7/7`。
- 期望值允许**多个可接受文件**（有些问题本来就有多个正确答案，硬指定单个会误判）。
- **评估集本身也要维护**：本次发现"为什么需要 Reranking"的期望值标错了——按文件名猜（问题含 "Reranking" 就写 `06_Reranking.md`），人工核对内容后才发现 `00_RAG.md` 里那段才是更直接的答案。
- 配套诊断工具：`test/inspect_query.py` 打印某问题在两阶段的逐条排名。**诊断脚本必须镜像生产逻辑**——曾因漏掉 `RECALL_N` 限制，看到"73 个候选"的假象。

## 四、踩坑清单

| # | 现象 | 原因 | 解法 / 教训 |
|---|------|------|-------------|
| 1 | `AttributeError: model_id` | 引用了 Config 里不存在的字段 | 字段名以定义处为准；顺手把命名统一（`emb_model` → `embedding_model`）|
| 2 | `Config()` 校验失败 | 字段改成必填后，`config or Config()` 不再成立 | 基类改 `Config.from_env()` |
| 3 | 装饰后的函数不是函数 | `@tool` 返回的是 `FunctionTool` 实例 | 想调用要 `.run(input=...)` |

## 五、调试方法（可迁移）

1. **一次只改一个变量**。同时改语料 + 切块参数 + 阈值，出了问题根本不知道是谁的锅。
2. **用数据定参数**：阈值、top_k、chunk_size 都先跑一次看分布/样本，再决定值，**不靠猜**。
3. **运行/编译是裁判，IDE 是助手**。遇到过三次编辑器误报（缩进错误、字段不存在），`py_compile` / 实跑一下就真相大白。
4. **打印数据结构比读文档快**：`message.model_dump()` 一打，`tool_calls` 的结构、`reasoning_content` 这类厂商私有字段全暴露了。
5. **先跑最小沙盒，再泛化**：先一个文件跑通切块 → 再 glob 全目录；先 3 块验证检索 → 再 198 块。
6. **别依赖服务端宽容**：你的代码要在严格服务端也能跑（供应商随时会换）。
7. **不报错 ≠ 没问题**：静默错误（重复调用、缓存用错模型）比崩溃更贵。
8. **任何断言都要实测**，包括别人的（包括 AI 给你的）结论。
9. **先证明"行为没变"，再看性能**：numpy 重构后先做一致性校验（矩阵版 vs 纯 Python 版最大差异 1.72e-15），确认排序不变，再测提速。**重构的铁律：优化不能改变行为。**
10. **排位异常要分阶段看**：检索结果不对，用 `inspect_query` 分别看余弦和 rerank 两个阶段，别对着最终结果猜。
11. **视图思维**：需要"同一份数据的另一种形式"时，优先建**视图**（numpy 矩阵、索引表），而不是复制一份存储再去同步两份数据。
