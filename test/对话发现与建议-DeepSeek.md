## 二、问题清单

### P1 ⭐ `llm.rerank` 的重试是空罩子 【已核实】

**状态**：✅ 已修（**你已实测通过**，见第七节）　**优先级**：高（原为"既有保护失效"）

**位置**：`retry.py:14-19` + `llm.py:74-91`

**现象**：`llm.rerank` 外面套着 `with_retry`，但**一次都不会触发**。

**证据链**（四步，每步都可单独验证）：

1. `with_retry` 只 catch `TRANSIENT_EXCEPTIONS`（`retry.py:32`），而这个元组里**全是 openai 的异常类**
2. 但 rerank 用的是 **`requests` 直发**（`llm.py:79`），因为百炼 rerank 是私有协议，OpenAI 协议里没有这个端点
3. `requests` 抛的是 `requests.exceptions.Timeout` / `ConnectionError` / `HTTPError` —— 与 openai 的异常类**没有任何继承关系**，一个都接不住
4. 连 `resp.raise_for_status()`（`llm.py:89`）抛的也是 `requests.HTTPError`，同样接不住

**结论**：这层重试对 rerank 的**全部真实失败模式**都不生效。网络一抖，直接失败。

**为什么危险**：这是"加了防御但防御不生效"。代码看起来有重试、有 `raise_for_status`、
有详细的注释说明为什么要调 `raise_for_status`——**读代码的人会以为这里是安全的**。

**建议改法**：给 `with_retry` 加一个 `exceptions` 参数：

```python
def with_retry(fn, *, what="调用", max_retries=MAX_RETRIES,
               base_delay=RETRY_BASE_DELAY, exceptions=TRANSIENT_EXCEPTIONS):
    ...
    except exceptions as e:
        ...
```

rerank 侧还要**按状态码分流**——`raise_for_status()` 对 4xx 和 5xx 抛的是同一个 `HTTPError`，
但 4xx（参数非法 / 认证失败）是**永久错误**，重试无意义，正是 `with_retry` 文档里说的"不浪费重试"：

```python
resp = requests.post(...)
if resp.status_code >= 500:
    resp.raise_for_status()        # 5xx → 交给 with_retry 重试
elif resp.status_code >= 400:
    raise ValueError(f"rerank 请求被拒（{resp.status_code}）: {resp.text[:200]}")
```

#### 实施记录（改动已落地，**你已实测通过**）

改了 **3 个文件**。三个设计决定值得单独记下来：

**① 默认的重试分类保持不变** —— `with_retry` 新增 `exceptions` 参数，
但**默认值仍是 `TRANSIENT_EXCEPTIONS`（openai 侧）**，只有 `llm.rerank` 显式传
`TRANSIENT_REQUESTS_EXCEPTIONS`。这样 `chat` / `stream` / `embed` / `execute_tool`
的行为与改动前**逐位相同** —— 改动是外科手术式的，不会顺带改变别处的行为。

> 顺带一条教训：**"临时错误"的分类应该按语义定，不能按"哪个库抛的"定。**
> 原来的分类是按库定的（全是 openai 的类），所以换一个 HTTP 客户端就整个漏掉，
> 而且不报错、不警告 —— 保护看起来还在。

**② `ALL_TRANSIENT_EXCEPTIONS` 只用于"报告"，不用于"重试"** ——
`execute_tool` 的 `except` 改用全集判断（好让"已重试多次仍未成功"这句文案
对 requests 侧的错误同样成立），但它**传给 `with_retry` 的仍是默认分类**（不重试 requests 错误）。

理由见新增的 **P12**：工具内部已经各自重试过了，外层再重试一次，尝试次数会**相乘**。
同一个"临时错误"标签，在"要不要重试"和"怎么报告"两处，答案可以不同 ——
因为**重试有放大效应，报告没有**。

**③ 4xx 走独立分支**：`status_code >= 400` 时抛 `ValueError`，不在重试清单里 → 一次就放行。
`raise_for_status()` 只留在 5xx 分支，所以它抛出的 `HTTPError` 放进重试清单是安全的。

具体改动：

| 文件 | 改了什么 |
|---|---|
| `retry.py` | 新增 `TRANSIENT_REQUESTS_EXCEPTIONS`、`ALL_TRANSIENT_EXCEPTIONS`；`with_retry` 新增 `exceptions` 参数（默认值不变） |
| `llm.py` | `rerank` 内按状态码分流（5xx 抛 HTTPError / 4xx 抛 ValueError）；调用处传 `exceptions=TRANSIENT_REQUESTS_EXCEPTIONS` |
| `tool_executor.py` | `except` 改用 `ALL_TRANSIENT_EXCEPTIONS`（只影响错误文案，不影响重试行为） |

**验证方法**（两个实验，一正一反，填进第七节）：

#### 已核实的事实

```python
# 修改前（现在注释保留在 RAG_tool.py:44-49）
for d, item in zip(batch, resp.data):     # 假设"返回顺序 == 请求顺序"
```

- 代码靠**数组位置**把向量配回文本
- OpenAI 协议的 embedding 响应里每项都带 `.index` 字段，**代码主动忽略了它**
- 更强的一点：OpenAI SDK 的 `Embedding` 模型把 `index` 定义成**必填字段**
  （`embedding: List[float]` / `index: int` / `object: Literal["embedding"]`），
  **所以这个字段一定拿得到、一定有意义，改起来不需要任何兼容判断**

#### 推测的风险（无证据）

"服务端可能乱序返回"—— 我**没有证据**说 DashScope 会这样，也举不出任何具体案例。
规范层面确实不保证顺序（`index` 字段存在的唯一理由就是不让你依赖位置），
但这是"依赖了 API 从未承诺的行为"，不等于"实际会违约"。

**准确的说法**：代码依赖了一个 API 从未承诺的行为；这个依赖目前看起来成立，但没有保障。

#### 真正具体、且不需要任何一方违约的风险：`zip` 静默截断

`zip` 在两边长度不一致时**按短的截断，而且不报错**。假设这一批 10 条、服务端只返回 9 条
（某条文本命中长度上限被拒，或降级返回了部分结果）：

```
batch:     [d0, d1, d2, d3, d4, d5, d6, d7, d8, d9]
resp.data: [r0, r1, r2, r4, r5, r6, r7, r8, r9]        ← 缺了 r3
zip 结果:   d0↔r0  d1↔r1  d2↔r2  d3↔r4  d4↔r5 …        ← d3 之后全部错位
```

**这里没有"乱序"，只有"少一条"，但结果是错位。** 而且最后的 `d9` 被无声丢掉，
store 只有 9 条 —— 块数少了你也许会察觉，**但中间那些错位的向量你永远发现不了**：
它们照样算得出分数、照样返回结果，只是答非所问。

这个机制比"服务端乱序"具体得多：**不需要任何一方违约，只需要一次部分失败。**

#### 你的实际修法（比我建议的更强）

```python
by_index = {item.index: item for item in resp.data}

if len(by_index) != len(texts):
    # 宁可炸,也不要静默错位——这里炸掉是有价值的失败
    raise RuntimeError(
        f"embedding 返回条数不符:请求 {len(texts)} 条,返回 {len(by_index)} 条"
    )

for j, d in enumerate(batch):
    item = by_index[j]  # 用 index 显式取,不靠位置
    store.append({...})
```

三个要点值得记下来：

1. **用 `index` 建映射,而不是用 `sorted` 排序** —— 排序只能纠正顺序，
   映射还能同时发现"某个 index 整个没来"。所以你这个写法**顺带把长度校验也做掉了**
2. **长度校验用 `raise` 而不是返回错误文字** —— 这是对的：
   `execute_tool` 那条"永不抛异常"是给**工具运行期**定的（错误要变成观察结果喂回模型自纠），
   而建索引是**初始化**，数据错了后面全错，**这种失败就该当场炸**
3. `index` 是**相对本次请求**的（0..9 这批内），不是全库编号 ——
   所以 `by_index[j]` 的 `j` 从 `enumerate(batch)` 来，正好对上

**收尾小建议**（⚪ 可选）：`RAG_tool.py:43` 那句注释还写着"**按顺序**把这一批的结果拼回 store"，
现在已经不按顺序了，注释和代码不一致。另外 44-49 行注释保留着旧实现 ——
留档符合你笔记的习惯，但注意它和 `cosine()` 不一样：`cosine()` 还在被 `__main__` 调用，

### P3 `_STORE` 和 `_INDEX` 没有联动失效 【整理时补充】

**状态**：🟡 建议改　**优先级**：中（现在无害，将来有害）

**位置**：`_STORE = None`（`RAG_tool.py:87`）+ `_INDEX = None`（`RAG_tool.py:130`）

**现象**：两个独立的模块级全局变量，各自惰性初始化，**没有任何重置入口**。

**为什么现在没问题**：没有任何代码会重置它们，所以两者永远同步。

**为什么将来会出问题**：路线图第 6 项"增量索引更新"一旦动手，就会出现
"重建了 `_STORE` 却忘了清 `_INDEX`"的情形 —— 你会**在旧矩阵上查新库**，
而且不报错。这又是一次"静默错误比崩溃更贵"。

**建议改法**：收成一个入口，让两者不可能脱钩。两种思路：

- 加 `reset_index()` 同时清两个全局变量，约定"重建必须走它"
- 更彻底：让 `get_index()` 只从 `get_store()` 派生，并检查 `store` 是不是同一个对象
  （`id(store) != _INDEX["store_id"]` 就重建视图）

**顺带**：这块也是"模块级可变状态"的代价 —— 两个全局变量让 `RAG_tool` 很难做单元测试
（每次测试要手动清全局）。如果哪天想给它补测试，这也是要先解决的事。

### P4 `retrieval` 的"永不抛异常"承诺只在生产路径成立 【已核实】

**状态**：🟡 建议改　**优先级**：中高

**位置**：`retrieval()`（当前 `RAG_tool.py:164-207`，函数体内无 try/except）+ `eval.py:42`

**现象**：`retrieval()` 内部调用 `embed()` 和 `llm.rerank()`，这两个是 **LLM 层**的东西，
重试用尽后**会抛异常**。`retrieval` 自己没有做任何捕获。

- **走生产路径**时没问题：`execute_tool` 有 `except Exception` 兜底 → 变成错误文字喂回模型 ✅
- **但 `eval.py` 和 `RAG_tool.__main__` 是直接 `.run()` 调用**，绕过了那层兜底 ❌

**为什么危险**：网络抖一下，`eval.py` 会**直接崩掉**，而不是报告"这个用例失败"。
你会以为"代码改坏了"，其实只是网络问题 —— 而 `eval.py` 恰恰是你后面每次改检索都要跑的东西。

**这是"契约由谁保证"的典型例子**：同一句"永不抛异常"，在生产路径成立，在测试路径不成立。
承诺写在一个地方，兑现靠另一个地方，中间没有编译器帮你检查。

> P2 的修法给了一个好的对照：那里我们**主动选择 `raise`**，因为"初始化数据错了"应当立刻炸。
> 而这里的 `retrieval` 是运行期工具，契约恰恰相反 —— **同一个文件里两种相反的契约并存，
> 靠的是读者知道"这是初始化还是运行期"**。这也是为什么要写清楚。

**建议改法**（二选一）：

- 让 `eval.py` 走 `tool_executor.execute_tool("retrieval", input=q, top_k=4)`，复用生产路径的契约
- 或者在 `eval` 里包 try/except，把异常计为"该用例失败（基础设施错误）"，与"检索没命中"区分开

**验证方法**：临时把 `LLM_BASE_URL` 改成坏地址跑 `eval.py`，看它是崩掉还是报告失败。

### P11 缓存指纹只认"输入变了"，不认"构建逻辑变了" 【整理时补充，已核实】

**状态**：🟡 建议改　**优先级**：中

**位置**：`_docs_fingerprint()`（当前 `RAG_tool.py:75-83`）
与 `get_store()` 的缓存命中判断（当前 `RAG_tool.py:107`）

**现象**：指纹 = `sha256(embedding_model + 每块 page_content + metadata)`。

它只覆盖**输入**。而下面这些改变的是"**索引是怎么构建出来的**"，指纹**一个都不管**：

- `build_store()` 的对齐方式（就是 P2 这次改的东西）
- `batch_size` 变化
- P10 里可能加的 `text_type="document"`
- 将来任何对 embedding 请求参数的调整

**后果**：改完构建逻辑，旧的 `.embedding_cache.json` 会被**原样复用**，
还会打印 `✅ 已从磁盘缓存加载向量索引（未重新调用 embedding）` ——
**这句话会让你以为新逻辑生效了，其实你查的还是旧逻辑建的索引。**

**这次为什么没出事**：因为假设"原来的顺序一直是对的"，那么旧缓存里的数据**碰巧仍然有效**，
不需要重建。但这个"碰巧"正说明指纹管不到这一层。

**建议改法**：加一个手工维护的版本号，参与指纹计算：

```python
INDEX_VERSION = 1     # 改 build_store 的语义 / embed 的请求参数时 +1

def _docs_fingerprint(documents):
    h = hashlib.sha256()
    h.update(str(INDEX_VERSION).encode("utf-8"))      # ★ 新增
    h.update(config.embedding_model.encode("utf-8"))
    ...
```

代价一行常量，收益是"改了构建逻辑忘了重建缓存"这类错误被**物理消除**。

**验证方法**：把 `INDEX_VERSION` 从 1 改成 2，跑一次，应该看到
`♻️ 检测到文档已变化，重新构建向量索引…`（而不是 `✅ 已从磁盘缓存加载…`）。

> 这条和 S8（全量指纹重建）是一对：S8 说"改一个字就要重建全部"（**太敏感**），
> P11 说"改了构建逻辑却不重建"（**太迟钝**）。同一个指纹机制，两个方向都漏。
> 合理的设计是**两层**：内容指纹管"语料变没变"，版本号管"构建逻辑变没变"。

### P12 重试嵌套导致尝试次数相乘 【整理时补充，已核实】

**状态**：🔴 待修（**现成补丁已给出，见下方"现成补丁"**）　**优先级**：中高

**位置**：`execute_tool` 的 `with_retry`（`tool_executor.py:98`）
× 工具内部各自的 `with_retry`（`llm.embed` / `llm.rerank`）

**现象**：同一份"重试保护"叠了两层，尝试次数**相乘**而不是相加。

以 `retrieval` 为例，如果 embedding 接口一直超时：

| 层 | 重试预算 | 实际请求数 |
|---|---|---|
| `llm.embed` 内的 `with_retry` | 3 次 | 4 次 |
| `execute_tool` 的 `with_retry` —— **它重跑的是整个工具** | 3 次 | × 4 = **16 次** |

退避时间也跟着叠加：内层每轮 1+2+4 = 7s，外层再加 1+2+4 = 7s，
**总共约 35s 才返回那句错误文字**。而这 35 秒里，你正在往一个**已经在故障中**的服务端
发 16 次请求。

**为什么现在没暴露**：`retrieval` 是唯一会发网络请求的工具，
而它的每一次网络调用都走 `llm.*`，**内部已经重试过了**。
换句话说，工具层这层重试**目前是 100% 冗余的**：

- `get_current_time` 不发网络请求，没有可重试的错误
- `retrieval` 的临时错误全部来自 `llm.embed` / `llm.rerank`，它们各自重试过
- 其他类型的错误不在 openai 那个元组里，外层根本不会重试

**为什么这算问题**：它违背了"一次只改一个变量"的精神 ——
调 `MAX_RETRIES` 的时候，你以为改的是"最多重试 3 次"，
实际影响是"最多 16 次请求、35 秒"。**参数名在骗人。**

#### 结论：删掉工具层这层重试。这不是取舍，是一个可以证明的删除

删除之前先问一句：**外层这层 `with_retry` 到底什么时候真的触发过？**

它用的是默认分类（openai 侧）。工具要抛出 openai 异常，只有一条路径：
工具内部调 `llm.chat` / `llm.embed` / `llm.rerank` —— **而这些方法自己全都带重试**。

逐个情形过一遍：

| 情形 | 外层会触发吗 | 有价值吗 |
|---|---|---|
| `retrieval` → `llm.embed` / `llm.rerank` 临时失败 | 会（异常类型在分类里） | ❌ 内层已经试过 4 次了 |
| 工具内部其他类型的错误 | 不会（不在分类里） | —— |
| `get_current_time` | 不会（不发网络请求） | —— |
| 将来 `search.py`（raw requests） | **不会**（requests 异常不在默认分类里） | —— |

**所以对当前代码库，外层重试是 100% 冗余。**
对它唯一会触发的情形，收益是"**在已经试过 4 次之后，再试 4 次**"。
删掉它不损失任何保护，只是把 4 倍的无谓请求和 28s 的无谓等待删掉。

还有一个反直觉的点：**重跑整个工具比分层重试更糟。**
一个多步工具（先检索、再加工）如果第二步临时失败，外层重试会把**第一步也重做一遍**——
既浪费，又可能不幂等。分层重试只重试真正失败的那一步。

> 考虑过但没采用的方案：**C（共享重试预算，往下传 deadline）** 在原理上最正确，
> 但要改所有层的签名，对一个学习项目是过重的基础设施。
> 而且只要"一次调用只在一层重试"这条纪律守住了，就不会再出现相乘 —— 纪律比机制便宜。

#### 现成补丁

`tool_executor.py` 的 `execute_tool`：

```python
    try:
        # 这里【不再】套 with_retry：工具内部的每一次网络调用（llm.embed / llm.rerank）
        # 都在自己那层退避重试过了。外层再重试一遍，重跑的是【整个工具】，
        # 尝试次数会相乘（4 × 4 = 16 次真实请求、约 35s），故障期间等于帮着打服务端。
        # 原则：重试放在拥有外部依赖的那一层；工具层只拥有"不抛异常"这个契约。
        return tool.run(**kwargs)
    except ALL_TRANSIENT_EXCEPTIONS as e:
        # 临时性错误能逃出工具 = 它内部各层已经退避重试用尽
        return f"工具执行出错（已重试多次仍未成功）: {type(e).__name__}: {e}"
    except Exception as e:
        return f"工具执行出错: {type(e).__name__}: {e}"
```

连带三处收尾（漏掉任何一处都会留下不一致）：

1. 文件头的 `from retry import ALL_TRANSIENT_EXCEPTIONS, with_retry`
   → **`with_retry` 变成未使用的 import**，要删掉
2. `execute_tool` 的 docstring 里那句"临时性错误（网络/超时/限流/5xx）：`with_retry` 自动指数退避重试"
   → 改成"临时性错误由各层（`llm.*`）自行退避重试，这里是最后一道兜底"
3. **`retry.py` 里的 `with_retry` 不动** —— 它还在给 `llm.chat` / `stream` / `embed` / `rerank` 用

#### 验证方法（有明确的 before / after 数字）

把 `LLM_BASE_URL` 改成坏地址，跑一次 `retrieval`，数 `⚠️ … 临时失败 …` 的日志行数：

| | 日志行数 | 耗时 | 返回给模型的错误文案 |
|---|---|---|---|
| **改前** | 约 15 行（12 条 embedding + 3 条工具） | 约 35s | "已重试多次仍未成功：…" |
| **改后** | **3 行**（只有 embedding） | **约 7s** | **完全相同** |

**错误文案不变 = 没有损失任何保护**，只是不再无谓地重跑整个工具。
