## 一、总体判断

**地基质量在个人学习项目里是上游水平；当前短板不在"功能不够多"，而在"没有回归保障"。**

已经做到位、值得保持的三个习惯：

1. **错误有分类学**：临时性错误（超时/限流/5xx）指数退避自愈，永久性错误变成观察结果喂回模型，工具层永不抛异常——错误被当成 Agent 循环的一等公民设计。
2. **参数是测出来的**：阈值 0.5 落在实测分布的空带里（相关 0.59~0.79 / 无关 0.40~0.42），top_k 与 overlap 的坑都是跑出来的数据。
3. **做过减法**：退役 Message 类、删掉文本协议的正则防线。知道什么该删比知道什么该加更稀缺。

短板一句话：**所有校准结论都靠人肉复跑验证**。现在改任何参数（chunk_size、阈值、换 embedding 模型）都是盲改，改完不知道是变好还是变坏。

## 二、代码层面的问题（按严重程度排序）

### 2.1 ⭐ 记忆管理在基类和子类里各有一份，基类那份有潜伏 bug

`Agent.add_message` 的裁剪是无脑切片：

```python
# agent.py —— 问题代码
if len(self._history) > self.config.max_history_length:
    self._history = self._history[-self.config.max_history_length:]
```

如果历史里是 `[user, assistant(tool_calls), tool]`，切片恰好从中间切走 assistant(tool_calls)，`tool` 消息就悬空了——严格服务端直接 400，这正是"设计演进笔记 2.4"里自己总结过的不变量（裁剪后第一条业务消息必须是 user）被基类违反了。

现在没炸只是因为 `ReActAgent` 绕开基类、自己维护 `messages` 并实现了正确的"裁到 user 边界"策略。结果就是：**同一个职责存在两份实现，正确的那份在子类，错误的那份在基类当死代码**。这比没有抽象更危险——哪天有人"用上"基类的记忆功能就踩雷。

**改法**：把 `_trim_history` 的策略（system 永远保留 + 裁到 user 边界）下沉到基类，两边共用一套记忆。这本身就是很好的重构练习，但**先做 3.2 的测试再动手**。

### 2.2 ✅ 已修复（10-03）重试逻辑放错了层：保护了工具，没保护 LLM

`TRANSIENT_EXCEPTIONS` 是 OpenAI API 层的临时错误，不只属于工具。现状是工具调用有退避重试，而主循环里 `llm.chat(...)` 裸奔——一次 429 整个 run 崩掉，工具的网络抖动反而能自愈，主次颠倒。

**改法**（直接沿用学习笔记 6.1 的教训"重试必须放在异常还活着的地方"）：把"指数退避重试"抽成通用函数，放进 `llm.py` 的 `chat`/`stream` **内部**——那是 openai 异常还活着的位置。工具执行路径已经覆盖，不用动。

> **修复记录（10-03）**：新建 `retry.py` 公共重试引擎（`TRANSIENT_EXCEPTIONS` + `with_retry`，重试用尽统一 raise）；`llm.chat`/`stream`/新增 `LLM.embed()` 走引擎、用尽上抛，`ReAct_agent.run` 里对 chat 调用兜底成"模型调用失败，请稍后再试"；`execute_tool` 换用引擎并保持"永不抛异常"契约（两个 except 分支区分"临时用尽"和"永久错误"）；`RAG_tool` 两处裸用 `client.embeddings` 改走 `LLM.embed()`。最终形态：**一个重试引擎、两种用尽策略，各层按自己的契约选**。
> 实际落地比原计划多走一步：原改法只想给 LLM 层加重试，动手时发现重试代码 90% 重复，顺势抽成了公共引擎——重复出现第二次就值得抽，不用等到第三次。

### 2.6 ✅ 已修复（10-03）工具参数只有"是合法 JSON"一级校验（评审时遗漏，讨论中发现）

> 本条不在初版评审清单里，是评审后讨论中发现的——评审也有漏网之鱼，记下来提醒自己：错误处理的检查点之一是"枚举所有可能传错的方式"。

json.loads 只能挡住"参数不是合法 JSON"，挡不住这些：漏传必填参数、编造不存在的参数名、类型给错（`top_k: "4"`）、loads 成功但不是字典（给了字符串或数组）。这些错误放过去会在 `tool.run(**kwargs)` 时炸成 Python 的 TypeError，被 `execute_tool` 的兜底 `except Exception` 转成内部报错文本喂给模型——模型收到 `missing 1 required positional argument...` 这种话，很难自我纠正。违背自己的原则："提示词只能'劝'，代码才能'管'"。

**改法**：做成 `ToolExecutor.validate_args(name, args)`——校验属于工具层（schema 归它管，和 schema 生成器构成契约的两半），Agent 循环只负责把错误字符串当作 tool 消息喂回模型，与"参数解析失败"走同一条通道；`execute_tool` 的 `except Exception` 兜底保留，从校验上线起只拦工具运行期真故障。

> **修复记录（10-03）**：`validate_args` 按顺序查：工具存在性 → 是否字典 → 缺必填/编造参数名（错误里列出可用参数）→ 类型比对。类型比对处理了 `isinstance(True, int) == True` 的坑——除 boolean 外先排除 bool，否则 True 会冒充 1 溜进去。9 种情况实测通过（缺参、编造参数名、str/float/bool 冒充 int、非字典、工具不存在、两个合法通过）。两个留档的取舍：① 类型校验先严格拒绝，模型有 max_steps 预算可自纠，观察一段时间再决定要不要宽松强转；② 校验器手写约 30 行，`jsonschema` 库留到参数类型复杂（anyOf/枚举）时再换。

## 三、缺失的两类"回归保障"（下一阶段的主题）

### 3.1 评测集（RAG 侧）

把手动校准固化成 `eval.py`：15~20 道题 + 期望命中的文件名，自动算 recall@k 和拒答正确率（无关问题必须拒答才算对）。`RAG_tool.py` 的 `__main__` 校准问题就是雏形。

**它是 rerank 的前置条件**：rerank 改变的是排序，没有评测集根本说不清它有没有用、top1 命中率从多少变成多少。

### 3.2 单元测试 + fake LLM（Agent 侧）

给 Agent 注入一个假 LLM（返回预置的 tool_calls 序列），主循环、裁剪、截断逻辑就能离线测试，不花 API 钱。最好的测试靶子（都是纯函数）：

- `_trim_history`（正好锁死 2.1 重构前后的行为一致）
- `build_parameters_schema`（正好锁死 2.3 修复前后的行为）
- `_is_noise`、`cosine`、`_clip_observation`

**有测试兜底，才敢动基类。**

## 四、rerank 之后的路线图

**关键认知：rerank 只能重排"已经召回的候选"，救不了召回**——第一步向量检索没把正确答案捞进 top_k，rerank 排得再好也没用。所以 rerank 之后的主题是把管线两侧补完整（`data/` 笔记目录就是现成的路标）：

| 顺序 | 功能 | 补哪一侧 | 笔记路标 |
|---|------|----------|----------|
| 0 | 评测集（见 3.1） | 保障，先于一切 | — |
| 1 | rerank | 精排 | 06 |
| 2 | Hybrid Search：BM25 + RRF 融合 | 召回 | 09 |
| 3 | Query Transformation：多查询改写 / HyDE | 召回（查询侧） | 12 |
| 4 | Parent-Child：小块检索、大块喂模型 | 粒度 | 05 |
| 5 | Metadata Filtering：工具加 filter 参数 | 范围 + schema 练习 | 07 |
| 6 | 增量索引更新：按文件粒度，替代全量指纹重建 | 索引维护 | 11 |
| 7 | Context Assembly：去重 / 头尾摆放 / token 预算 | 生成侧 | 13 |

几条理由展开：

- **2 在 1 后面是黄金搭档**：BM25 补向量检索对中文关键词/专有名词的短板，RRF 融合出候选集再交给 rerank 精排——工业界标准的两阶段检索。
- **6 会被 2~5 逼出来**：现在缓存是全量指纹，改一个字全部重建；等管线变复杂，重建成本变成真痛点，增量更新才有练手的价值。
- **Agent 侧穿插项**（排在管线成型之后，避免两条线同时改把评测搞混）：
  - 接入 `search.py`："库内优先、库外搜索"策略，逼出工具选择与多信息源组合问题
  - 流式输出（进阶：流式收集 tool_calls 的 delta，而不是"先非流式跑完再流式重说一遍"）
  - Plan-and-Solve（`test_plan_and_solve.py` 半成品）、多智能体

一句话记管线结构：**2、3 补召回侧，4、5 补粒度和范围侧，rerank 居中管精排，6、7 管索引维护和生成侧。**

## 五、执行原则

沿用演进笔记第五节，新增一条：

1. **一次只动一个变量**——语料、切块参数、阈值不同时改。
2. **有 eval 才敢迭代**——先评测集，再动管线；每改一条跑一遍。
3. **（新）动基类前先给现有行为补测试**——重构 = 测试先行，没有锁死行为的测试，"重构"和"重写"没法区分。
